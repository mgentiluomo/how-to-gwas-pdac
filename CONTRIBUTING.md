# Contributing

Thank you for contributing to the GWAS guide. This file explains **how we work
together** so that everyone builds on the same, consistent base of files.

The golden rule: **`main` is protected.** It always reflects the agreed,
harmonised version. You never commit directly to it — you propose changes
through a Pull Request (PR), which a maintainer reviews and merges.

Maintainers (the only people who merge to `main`):
**Manuel Gentiluomo** and **Riccardo Farinella**.

---

## 1. One-time setup

```bash
# clone the repository
git clone https://github.com/<OWNER>/how-to-gwas-pdac.git
cd how-to-gwas-pdac

# tell git who you are (so your contributions are attributed correctly)
git config user.name  "Your Name"
git config user.email "your.email@institution.edu"
```

If you do not yet have write access, ask Manuel to add you as a collaborator,
or fork the repository and open PRs from your fork.

---

## 2. The day-to-day workflow

1. **Sync** with the latest `main` before starting:
   ```bash
   git checkout main
   git pull
   ```
2. **Create a branch** for your work. Use the convention
   `section<NN>-<short-topic>`:
   ```bash
   git checkout -b section02-pca-draft
   ```
3. **Work inside your section folder** (`sections/<your section>/`). Add your
   Markdown text and your annotated scripts there. Do not edit other people's
   sections without coordinating first.
4. **Commit** in small, clear steps:
   ```bash
   git add sections/02_population_stratification/
   git commit -m "Section 2: first draft of PCA narrative + plink2 PCA script"
   ```
5. **Push** your branch and **open a Pull Request** to `main`:
   ```bash
   git push -u origin section02-pca-draft
   ```
   Then open the PR on GitHub and request review from a maintainer.
6. A maintainer reviews, may ask for small edits, and **merges**. After merge,
   delete your branch and start the next piece from a fresh `main`.

> Working on the same files at the same time? Pull often and keep branches
> short-lived to avoid conflicts.

## 3. Code style (kept uniform on purpose)

- **Languages/tools:** PLINK 2 and R only, unless agreed otherwise.
- **One step = one script**, numbered, self-contained, and **heavily commented**
  — remember the audience has no bioinformatics background. A reader should
  understand *why* each flag/option is used, not just *what* it does.
- Every script **prints the command for the next step** at the end.
- Use the demo dataset (`demo_dataset/`) as the running example so all sections
  are consistent. Do **not** introduce a different example dataset without
  agreement.
- Make randomness reproducible: expose a `--seed` (default `2026`).
- Assume genome build **GRCh38**.

---

## 4. Documentation & references

- Write narrative in **Markdown**.
- Cite as provisional placeholders: `[DOI/PMID]` in square brackets,
  **highlighted yellow**. Final formatting will be harmonised to **Vancouver**
  style by the editors.
- Keep figures in `docs/` (PNG/PDF, 300 dpi).

---

## 5. What must NOT go into git

- Raw or intermediate genotype data (`*.bed/bim/fam`, `*.pgen/pvar/psam`,
  `*.vcf*`, downloaded HAPNEST files). These are large and are regenerated by
  the scripts. The `.gitignore` already excludes them.
- Any real, access-controlled individual-level data (e.g. dbGaP / PANSCAN). The
  demo example uses only the **synthetic** HAPNEST data.
- Credentials, tokens, absolute local paths.

Commit only: scripts, Markdown text, final summary statistics, and figures.

---

## 6. Questions

Open a GitHub **Issue** for anything that needs group discussion (scope of a
section, an overlap between sections, a data question). Use Issues rather than
email threads so the decision is visible to everyone and stays with the code.
